# ChatBucket B2B Backend — Node.js port

A TypeScript/Express port of the FastAPI service in `../chatbucket_b2b_backend`.

**Status: foundation complete, ~15% of endpoints ported.** This runs, is tested,
and interoperates with the Python service — but it is not yet a replacement for
it. See [What is left](#what-is-left).

---

## Why it is built this way

The port's one hard constraint is that **both services run against the same
MongoDB during the cutover**. That is what makes the migration safe: you can
serve traffic from Python, answer the same request from Node, and compare, rather
than switching everything over and hoping.

Everything below follows from that constraint.

### The crypto is wire-compatible, deliberately

`src/security.ts` reproduces `app/security.py` exactly:

| | Format |
| --- | --- |
| Passwords | `pbkdf2_sha256$240000$<salt_hex>$<hash_hex>` — PBKDF2-HMAC-SHA256, 16-byte salt, 32-byte output |
| OTP codes | HMAC-SHA256 under `JWT_SECRET`, hex |
| API keys, opaque tokens | SHA-256, hex |

bcrypt or argon2 would be a better choice for a greenfield service and are the
**wrong** choice here: switching would lock out every existing customer on the
first request. `npm run test:parity` asserts this against fixtures generated by
the Python code — not against Node's own output, which would pass while
everybody was locked out.

Verified working in both directions:

- a password hashed by Python verifies in Node;
- an OTP issued by Node was verified by the Python service, against the same
  database, over HTTP.

`JWT_SECRET` **must** be identical in both services. A token issued by one has to
be accepted by the other while traffic is split, and outstanding OTPs are keyed
under it.

### Money is the part to be careful with

`src/money.ts` is the riskiest file in the port. Python has exact decimals
natively; JavaScript has only float64, where `0.1 + 0.2 === 0.30000000000000004`.
That error compounds the moment Mongo `$sum`s thousands of usage rows into an
invoice total.

Amounts move through three representations and that module owns the edges:
`Decimal` (decimal.js) for arithmetic, `Decimal128` for storage, and `number`
**only** on the JSON wire. Nothing outside `money.ts` may call `Number()` on an
amount. If you want to, you want `toJson` and you are about to write a billing
bug.

### Two pydantic behaviours had to be rebuilt by hand

zod is not pydantic. `src/schemas/auth.ts` restores both behaviours the frontend
already depends on:

- **camelCase and snake_case are both accepted** (`withAliases`), because the
  frontend posts `howDidYouHear` and older integrations post `how_did_you_hear`;
- **unknown fields are rejected, not dropped** (`.strict()`). zod's default is to
  strip them, which means a form posting a field the API does not model gets a
  201 and loses it silently.

`src/errors.ts` renders validation failures in FastAPI's `{detail: [{loc, msg,
type}]}` shape, because the UI reads it per field.

## Running it

```bash
npm install
cp .env.example .env      # set JWT_SECRET to the SAME value as the Python service
npm run dev               # http://127.0.0.1:8001
```

Port 8001 by default, so it runs **alongside** the Python service on 8000 and the
two can be compared request by request.

```bash
npm run typecheck         # tsc --noEmit, strict
npm run test:parity       # 19 checks: cross-language crypto compatibility
npm test                  # 37 checks: end-to-end against a real MongoDB
npm run build && npm start
```

`npm test` uses a throwaway database (`chatbucket_b2b_nodetest`), dropped at both
ends, and a real MongoDB rather than a mock — the behaviour being tested is
largely *in* MongoDB (unique indexes, TTL expiry, atomic `$inc` under `$gte`),
and a mock that reimplemented those would be testing the mock.

## What is ported

```
src/
  config.ts                 The ONLY module that reads process.env
  logger.ts                 Level-aware logging + log-injection guard
  errors.ts                 HttpError, FastAPI-shaped 422s, asyncHandler
  money.ts                  Decimal / Decimal128 / number — the three edges
  security.ts               Passwords, JWT, API keys, OTP hashing
  database.ts               Connection, collections, every index
  serialization.ts          publicUser (allow-list, never deny-list)
  schemas/auth.ts           zod bodies, E.164 normalisation, aliasing
  middleware/ratelimit.ts   Counted in Mongo, so it holds across workers
  services/
    sms.ts                  The one place a text is sent; DLT rules
    verification.ts         Channel rule + pre-registration phone proof
    credits.ts              Atomic debit, ledger on every movement
  routes/auth.ts            register, login, verify-phone, verify-phone/resend
```

### Behaviour carried over that is easy to lose

**An Indian number verifies by SMS and gets no email code**; everywhere else
verifies by email. `verification.channelFor` is the single place that rule lives.

**The number is proven before the account exists.** The signup form verifies the
mobile while the rest of the form is being filled in, so there is no user
document to hang the code off — `phone_verifications` holds it, keyed by the
number, and register reads the result. A number proven within
`PHONE_VERIFICATION_GRACE_MINUTES` creates the account already verified and is
not sent a second code; the record is then consumed, so one proof cannot be spent
on several accounts each collecting the signup bonus.

**A number already registered and verified gets a 409**, not a generic "a code
has been sent". Silence there kept no secret — register already refuses a taken
number with a 409 — while leaving people on the signup form waiting for a message
that was never going to be sent.

**`SMS_TEMPLATE_SUFFIX` defaults to empty.** TRAI requires the sender header and
message template to be pre-registered on a DLT platform, and an unregistered pair
is dropped by the *operator*, not the gateway: the gateway still answers 200 and
its delivery report still says `Delivered`. A trailing word the registration does
not have breaks the match invisibly. This is not hypothetical — a guessed suffix
did exactly that in the Python service until it was emptied.

**Login hashes even when no user matched**, against a dummy hash of the same work
factor, so the miss path does not return visibly faster and turn the endpoint
into an account-enumeration oracle.

than translating.

## Cutover

Do not switch DNS at a Node service that has merely passed its own tests. Run
both, send the same requests to each, and diff the responses — the databases are
shared, so this is safe and cheap. Only cut over once the suites and the real
responses agree.
